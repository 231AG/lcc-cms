# Local Development Setup

## Prerequisites

- Node.js 20+ and npm
- Docker Desktop (for local Postgres — used for development and for integration tests, which
  run against a real Postgres per the plan's testing strategy, Section 23.1)

## First-time setup

```bash
npm install
cp .env.example .env.local
docker compose up -d          # starts local Postgres on localhost:54329
npm run db:migrate            # applies every migration in ./drizzle, in order
npm run db:seed               # idempotent reference data: grade scale, institution settings
npm run dev
```

## Environment variables

See `.env.example`. `DATABASE_URL` defaults to the local Docker Postgres. To point at a Supabase
project instead (its connection string, pooler in **transaction mode**), use that project's
connection string here — never a browser-exposed key. `NEXT_PUBLIC_SUPABASE_URL` and
`NEXT_PUBLIC_SUPABASE_ANON_KEY` are safe for client code; `SUPABASE_SERVICE_ROLE_KEY` is
server-only and must never be exposed to client code, logged, or committed.

## Everyday commands

| Command | What it does |
|---|---|
| `npm run dev` | Start the Next.js dev server |
| `npm run db:migrate` | Apply pending migrations |
| `npm run db:generate` | Generate a new migration from schema changes in `src/lib/db/schema/` |
| `npm run db:seed` | Re-run the idempotent reference-data seed |
| `npm run test` | Run the full test suite (needs Postgres running — see integration tests below) |
| `npm run lint` / `npm run typecheck` | Static checks (`typecheck` runs `next typegen` first — see note below) |
| `npm run build` | Production build |

## Database migrations

Forward-only, checked in as plain SQL under `drizzle/`, applied in order (plan Section 10.7 / 30.3).
Never make a schema change through a hosted console in any environment — that is the drift risk the
plan calls out explicitly (Section 6.3). A mistake is fixed by a new migration, never by editing an
applied one.

Some migrations are hand-written (not generated by `drizzle-kit generate`) because RLS policies and
privilege grants aren't expressible in the Drizzle schema DSL — see `drizzle/0001_audit_privileges.sql`
for the pattern: create it with `npx drizzle-kit generate --custom --name=<name>`, then write the SQL
by hand.

## Integration tests

Files named `*.integration.test.ts` run against the real Postgres from `docker-compose.yml` — row-level
security, privilege grants, and transaction behavior cannot be verified against a mock (plan Section
23.1). Make sure `docker compose up -d` and `npm run db:migrate` have been run first.

## Why `typecheck` runs `next typegen` first

Next.js generates ambient route types (e.g. `LayoutProps<"/">`) into `.next/types/` during `dev` or
`build`. Running `tsc --noEmit` cold, before either has ever run, fails on those names. `next typegen`
generates just the types without a full build.

## Three environments

Per the plan (Section 8.5), development, staging, and production must be three separate Supabase
projects — never the same project, never separate schemas in one project. `.env.local` is
git-ignored and holds whichever environment you're pointed at locally; it is never committed.
